# 今天吃什么：自适应推荐与界面设计

状态：已确认采用方案 B（两参数模型）、本地优先的桌面应用，并支持安卓。采用 Dioxus + Rust + SQLite，首版业务已实现；安卓 APK 已构建，尚待真机验收。见 [架构文档](architecture.md)。

## 已确认的产品语义

- 第一版个人使用，桌面与安卓各自保存本地数据，支持备份与恢复；为未来多用户保留数据归属。
- 一次只展示一个可直接选择的用餐选项，例如牛肉面、麻辣烫、套餐。
- 用户点击“吃”或“不吃”。“吃”直接记录为这顿吃了，允许撤销与修改；“不吃”展示下一个不同选项。
- 学习的是“上次吃过，到再次想吃”的间隔，不是两次展示之间的间隔。
- 界面要夸张、有表现力，决策路径保持简单。

本方案替代此前固定 7 天恢复权重、一次多个候选的草案。

## 收敛目标

每个“用户 × 用餐选项”维护一个恢复周期 T_i，含义是：距离上次吃过 T_i 天时，模型预测再次选择“吃”的概率达到 q。

建议初始 q = 0.7、T_i = 7 天。70% 是用来定义周期的可调设计目标，不是全局推荐命中率承诺，也不是从用户历史得出的事实。T_i 是连续曲线的参考点，不是禁止提前推荐的冷却时间，更不是保证在那一天展示的排期。

## 概率模型与在线学习

用户已选定模型 B，每个用户档案与食物学习两个参数 a、b：

```text
x = ln(1 + d)，d 为距上次实际食用的天数
p(d) = sigmoid(a + b x)，b ≥ b_min > 0
T(q) = max(0, exp((logit(q) − a) / b) − 1)
```

初始化建议 q = 0.7、b0 = 2、a0 = logit(0.7) − 2ln(8)，对应 7 天参考周期。两个参数都参与学习，模型 A 仅作为对照。

对具有已知食用起点的反馈，y=1 表示吃，y=0 表示不吃。令 e=p-y，带先验正则的更新为：

```text
a ← a − η [e + λ(a − a0)]
b ← max(b_min, b − η [e x + λ(b − b0)])
n ← n + 1
```

两项使用更新前的同一快照计算；η 随该选项的有效反馈次数递减。当前实现 η = 0.08 / (1+n/8)^0.65、λ = 0.002，a 投影到 [-30,30]，b 投影到 [0.05,20]。这些是实验初值，尚未经过真实用户校准。反馈学习使用食用时间归零前的间隔，然后再写入这顿的实际食用记录。

详细定义、梯度与收敛条件见 [恢复周期模型比较](algorithm-options.md)。方案 B 仍假设长期接受率趋近 1；永久不喜欢用显式停用表达。

## 单项推荐策略

1. 筛选属于当前用户、启用且本次用餐决策尚未出现过的选项。
2. 计算各选项此刻的 p_i(d)。
3. 令 w_i = p_i(d)^2；采用混合抽样：π_i = 0.9 × w_i / Σw + 0.1 / N。
4. 按 π_i 抽取一个选项，记录展示事件与上下文。
5. “不吃”仅排除本次决策中的该选项并更新模型；“吃”更新模型、记录本餐并结束决策。

p_i 是预测用户想吃的概率，π_i 是系统抽中该选项的概率，二者不同。10% 的均匀探索只作用于合法候选，目的是让暂时低估的选项还有反馈机会；不允许绕过用户停用或其他硬性限制。

一轮全部拒绝后明确显示“这轮都不想吃”，允许手动记录别的食物或之后开启新一轮。不能在原决策里无限循环刷同样的选项。界面重绘、刷新和请求重试都返回同一张尚未回答的卡，不产生额外训练样本。

## 冷启动、反馈噪声与收敛边界

- 没有食用记录时，无法知道恢复时间从何时开始。将其作为新选项探索，暂取排序分数 p = 0.5；这个值只是冷启动约定，不是校准过的预测。
- 新选项被拒绝只影响本轮排除，不训练恢复周期；首次接受后产生真实起点。用户也可以补录上次吃过的日期。
- 关闭页面、未回答、动画期间重复点击都不算“不吃”。
- 拒绝可能来自预算、天气、距离或临时心情。二元反馈无法识别原因；初版把它视为噪声，不把某次拒绝直接解释为长期厌恶。
- 对永远不想吃的选项，目标接受率可能根本不可达。支持用户明确停用，推导周期超出合理范围时也不能标记“已收敛”。
- 若用户偏好相对稳定、模型合理、各选项持续获得足够反馈，则递减步长满足 Ση = ∞、Ση² < ∞，可在适当的随机近似条件下讨论参数收敛。此处不承诺任意真实用户行为下的严格收敛。
- 收敛指参数与预测逐渐稳定；每次二元选择仍可随机变化。少量反馈或学习率已很小时，更新变小本身不是学准了的证据。
- 永久收敛和持续追踪口味变化有冲突。初版使用递减步长验证稳定偏好；后续如加入学习率下限或遗忘机制，应改称跟踪一个范围，不能继续承诺严格点收敛。

## 架构

采用 Dioxus 0.7 + Rust + rusqlite/bundled SQLite。RSX 界面直接调用本机 Rust 业务核心，模型和数据库在设备内运行。

```text
Dioxus RSX 界面（桌面 / 安卓）
  ↓ Rust Command + 阻塞工作线程
Rust 应用服务
  ├─ 推荐与两参数学习
  └─ 事务、历史、撤销与重建
       ↓
     本机 SQLite
```

“反馈—学习—记餐/下一候选”作为一个事务提交；撤销时纠正历史并重建受影响模型。启动或恢复时从数据库取得当前决策，不把界面内存视为权威数据。

具体模块、数据表、命令、平台差异及备份/同步边界见 [架构文档](architecture.md)。

## 视觉与交互方向

方向：夸张的街头海报 / 游戏选人画面。大字、撞色、粗边框和倾斜标签围绕唯一候选展开；不给用户堆候选列表。

- 主体：巨大食物名称，配一条事实描述，例如“上次吃是 8 天前”；初版不展示未经校准的“命中率”。
- 操作：两个足够大的按钮，“不吃，换一个”和“吃，就它了”。
- 拒绝：当前卡片甩出，下一项入场；不把拒绝表现成犯错或惩罚。
- 接受：短促的盖章或庆祝动效，显示“已记入这顿”，同时提供撤销。
- 减弱动态效果设置下使用静态切换；不做持续闪烁、强制等待或自动播放声音。
- 参数、探索比例和模型版本留在调试界面，主流程只负责做选择。

会话中的交互草图仅演示这些状态，不连接真实数据库，也不把演示点击当作真实饮食记录。

## 历史实验与待验证事项

现有 `experiments/interval_learning.py` 只验证此前的模型 A，不是所选模型 B 的验证结果。B 现有 `tests/flows.rs` 的固定种子合成反馈测试：10,000 次反馈后预期对数损失从 0.2638 降至 0.2562（生成模型为 0.2464），验证有学习效果但不等价于真实使用下的收敛。以下保留 A 的历史实验：对真实周期分别为 2、7、20 天的三个模拟选项，每天两次用餐决策，执行单项抽样、拒绝换项、接受重置时间及递减步长更新。用多个随机种子比较短期和长期估计。

模拟用户按同一逻辑曲线产生反馈，因此该实验仅检查公式与调度闭环的可行性，不是模型适合真实用户的证据。上线前还应检查错设曲线、口味变化、永久拒绝、未回答、补录撤销、候选不足和重复请求。

30 个固定随机种子的估计中位数如下（单位：天）：

| 模拟用餐决策次数 | 真实周期 2 天 | 真实周期 7 天 | 真实周期 20 天 |
| --- | --- | --- | --- |
| 120 | 1.93 | 6.81 | 18.11 |
| 1,000 | 2.01 | 7.06 | 20.27 |
| 10,000 | 2.01 | 7.02 | 19.75 |

前 120 次决策中，各选项有效反馈次数中位数约为 105、72、63 次；候选增多时每项反馈会更少。10,000 次仅用于观察长期行为，不能当成真实产品可接受的学习时长。脚本同时输出跨种子的估计范围，避免把中位数误认为每次运行都达到的精度。
